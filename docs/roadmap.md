# Roadmap — PR sequence

Each phase is its own branch and pull request into `claude/hello-mt20cg`.
Nothing merges without review; nothing in a later phase starts until the
current one is approved.

**This completes the bare-minimum end-to-end MVP**: a person can open the dashboard, fetch real Gmail/Calendar data for a process, see Claude's plain-language summary and proposed next action, approve or reject it, and see the result — all with status/audit persisted for later. Excel is built (phase 4) but not yet wired into the agent/API/UI (needs a workbook item id as extra input) — a natural phase 7 candidate.

**Post-MVP hardening, found by real testing (not separately numbered phases, each its own PR):** a reasoner JSON-parsing crash on a markdown-fenced response; the reasoner fabricating a placeholder recipient when no real one was in the fetched data (now hard-refused at the tool layer, RFC 2606 reserved domains); no retry on a transient network error during a read, and a raw 500 instead of a clean API error; the approval card showing a raw payload dict instead of labeled fields; and — directly serving the "recognise when something has stalled" / "continuous learning from outcomes" goals in the original concept doc — the reasoner now classifies each situation with a stable category slug (e.g. `shipment_delay`), color-coded consistently in both the approval card and the History table, so a recurring pattern across different processes (three orders delayed by the same supplier issue, say) is visually obvious rather than three unrelated-looking approvals.

| 7a | `claude/apm-07a-intent` | Free-text intent parsing: `ClaudeIntentParser` (`src/apm/agent/intent.py`), same protocol-based pattern as the reasoner, turns a plain-language request ("chase up order 4521", "check the Acme renewal") into a process id + Gmail/Calendar queries. New `POST /query` endpoint runs it straight through the existing graph, reusing known process ids from the state store so a follow-up request continues the same order instead of minting a new one. | Yes (Anthropic API key) to run for real; fully unit-tested with a fake parser without it |
| 7b | `claude/apm-07b-ui-rework` | NiceGUI rework (`src/apm/ui/app.py`): replaces the old process-id/Gmail-query/Calendar-query form with a single free-text prompt bar wired to `POST /query`, an orders list home page (from `GET /processes`, status pill derived from each process's stage — `src/apm/ui/logic.py`'s `order_status`) sorted most-recently-updated first, and a per-order detail page (`/orders/{process_id}`) with the summary, approval card, and history, reusing the phase 6b formatting helpers. Verified end-to-end in a real browser (Playwright) against fake tools: ask → resolve → approve → history/orders-list update, plus the unknown-order and empty-input edge cases, with zero console errors. | Same as 7a to run for real; fully unit-tested (`tests/test_ui_logic.py`) without it |

**Automated UI test suite + demo data (not a numbered phase, its own PR):** `tests/test_ui_pages.py` drives the actual dashboard pages via NiceGUI's official `user` test fixture (`nicegui.testing.user_plugin`, registered in the root `conftest.py`) — typing into "Ask APM", clicking it, approving/rejecting, checking the orders list — with `httpx.AsyncClient` monkeypatched to an in-process fake API app (fake Gmail/Calendar clients, fake reasoner, fake intent parser), so it runs on every `pytest` invocation with no live credentials, browser, or running server, unlike the one-off manual Playwright check phase 7b was verified with. `scripts/seed_demo_data.py` seeds a real sandbox account with six emails and two calendar events across five categories (three `shipment_delay` orders on purpose, so the category color-coding has a genuine repeat to demonstrate) for demoing the end-to-end flow against real data.

**`reset-demo-data` skill (not a numbered phase, its own PR):** `scripts/reset_demo_data.py` + `.claude/skills/reset-demo-data/SKILL.md` — clears local `state/` (and, opt-in, cached OAuth tokens) so demo runs start from a clean slate, and prints the exact manual cleanup steps for the real Gmail/Calendar seed data (no delete capability exists on the tool connectors — see `docs/capability-map.md` — so that part is deliberately manual, not automated).

**Excel files: local + Google Drive connector (not a numbered phase, its own PR):** `src/apm/tools/excel_file_tool.py` — a second Excel connector alongside the phase 4 Microsoft Graph one, for workbooks that are plain `.xlsx` files rather than something already on OneDrive/SharePoint: a `WorkbookSource` abstraction (`LocalWorkbookSource` for a path on disk, `GoogleDriveWorkbookSource` for a file id, downloaded/uploaded via the Drive v3 API and reusing the Gmail/Calendar Google OAuth client with its own token cache) supplies whole-workbook bytes, parsed/edited with `openpyxl`. Same read-then-dry-run-gated-write shape as every other connector — list worksheets, read a range, and `write_range`. `scripts/excel_file_demo.py` is the manual smoke test; `tests/test_excel_file_tool.py` is fully unit-tested with a fake in-memory source, no credentials needed even for the Drive path's logic. See `docs/capability-map.md` for the full writeup, including the local-vs-Drive scope and known gaps (Drive mode only handles an uploaded `.xlsx`, not a native Google Sheet).

**Excel wired into the agent graph + business-scenario tests (not a numbered phase, its own PR):** `fetch_node` (`src/apm/agent/graph.py`) gained an `"excel_file"` branch alongside its existing `gmail`/`google_calendar`/`ms_excel` ones — `execute_node` already dispatched to any tool/method by name, so this was the one piece missing to run the connector through the full fetch → summarize → propose → **human-approval interrupt** → execute cycle. `tests/test_agent_graph.py` adds a "renewal tracker" business scenario (mirroring the existing shipment-delay/renewal-reminder tests for Gmail/Calendar): the agent reads a renewals worksheet, proposes logging that a customer's renewal was contacted by updating the tracker, and the row is only actually written after an approval — rejected the same way, nothing is written — using a fake in-memory workbook source, no live credentials needed.

**Excel wired into the API/UI (not a numbered phase, its own PR):** closes the "extra input" gap noted in phase 6b/7b above — Excel needs to know *which* workbook, unlike Gmail/Calendar's "the account". Two decisions made explicitly rather than assumed: (1) one workbook per running server, configured via `APM_EXCEL_WORKBOOK_PATH` (local) or `APM_EXCEL_DRIVE_FILE_ID` (Drive) — `apm.tools.excel_file_tool.build_configured_excel_tool` builds it (or returns `None` if unconfigured, or raises if both are set), added to `apm.api.dependencies.get_graph`'s tools when present; (2) reached through the dashboard's existing free-text "Ask APM" box rather than a separate form field — `apm.agent.intent`'s `ParsedIntent` gains `excel_query: bool`, and `ClaudeIntentParser`'s prompt now recognizes spreadsheet-sounding requests ("check the invoice tracker") as a yes/no signal to fetch the configured workbook's default range (its first sheet, whole used range — the parser has no visibility into the workbook's actual layout, so it can't propose a sheet/address, only whether to look at all). `apm.api.app`'s `/query` route and `_build_queries` pass that signal through; `excel_query=True` with no workbook configured is a harmless no-op (fetch_node already skips a tool that isn't in `tools`). The approval card needed no changes at all — `apm.ui.logic.format_action_details` already had a `write_range` case (Sheet/Range/Rows) from when the MS Excel connector was built. Verified with a real end-to-end pass through the actual dashboard pages (`tests/test_ui_pages.py`'s `test_excel_renewal_tracker_approval_flow_through_the_ui`), not just the API/logic layers in isolation. **`excel_file` (local/Drive) is deliberately the only Excel connector the API/UI wires in** — `apm.api.dependencies.get_graph` never builds an `ms_excel` (Microsoft Graph) tool, so it stays available but dormant: `fetch_node`/`execute_node` already handle its `"ms_excel"` tool key generically, and onboarding it later needs only a `build_configured_ms_excel_tool`-equivalent factory plus env vars in `dependencies.py`, mirroring `excel_file`'s. Documented explicitly in `docs/capability-map.md`/`.env.example` rather than left as an accident of build order, since a separate Azure AD app registration is exactly the kind of setup most deployments won't want by default.

**Reasoner now receives the user's own request, not just fetched data (not a numbered phase, its own PR):** found via a real "update order 223's status to Paid" request — the reasoner replied with a summary noting the order was unpaid and proposed a payment-follow-up *email*, which then failed for lack of an address, instead of updating the tracker as asked. Root cause: `/query` resolved the user's free-text ask to a process id + queries via `apm.agent.intent`, then discarded the text itself — `reason_node` (`src/apm/agent/graph.py`) called `reasoner.reason(process_id, fetched_data)` with no way to distinguish a specific instruction from a plain "check on this," so `apm.agent.reasoner.SYSTEM_PROMPT`'s generic "propose whatever would help" heuristic won by default. `start_process` gains an optional `request_text` parameter, threaded through `GraphState` into `reason_node` and the `Reasoner` protocol's `reason()` (now `(process_id, context, request_text=None)`); `apm.api.app`'s `/query` route passes `body.text` through. `SYSTEM_PROMPT` now instructs: when a request is given, propose the action that directly fulfills it (still bound by the existing "never invent a value not in the fetched data" rule) rather than substituting a different, independently-guessed action; fall back to guessing only when there's no request (e.g. a plain "check on order 4521"). `/start` (explicit query fields, no free-text box) is unaffected — `request_text` defaults to `None` there. Regression-guarded at three layers: `tests/test_reasoner.py` (the prompt text itself), `tests/test_agent_graph.py` (`request_text` reaches `Reasoner.reason`), `tests/test_api.py` (`/query`'s `body.text` reaches the reasoner end-to-end).

**Core dependencies split from the NiceGUI dashboard's (not a numbered phase, its own PR):** first step of decoupling the integration layer (`src/apm/tools`/`agent`/`state`) plus its API (`src/apm/api`) into something shippable on its own to a future presentation layer (e.g. voice/LiveKit) — same motivation as `docs/architecture.md`'s Layer 2. `requirements.txt` mixed `nicegui` in with every core dependency, so `pip install .` still pulled in the dashboard's stack even though `apm.ui` was already (per phase 6b) only an HTTP client of `apm.api`, never an importer of `apm.agent`/`apm.tools`. `pyproject.toml` now declares core deps under `[project.dependencies]` and splits `nicegui`/`httpx` into a `ui` extra (`pip install .[ui]`) and `pytest`/`pytest-asyncio`/`httpx` into an `integration-layer` extra; `requirements.txt` is removed as a second source of truth. The root `conftest.py`'s `pytest_plugins` registration for `nicegui.testing.user_plugin` is now conditional on nicegui being importable, with `tests/test_ui_pages.py` (the only test module that imports `nicegui` directly) added to `collect_ignore` when it isn't — verified by running the full suite in two throwaway venvs, `pip install -e .[integration-layer]` (129 passed, no nicegui installed at all) and `pip install -e .[ui,integration-layer]` (135 passed, the six `test_ui_pages.py` cases included). See `docs/running-locally.md` for the day-to-day commands. `scripts/gmail_demo.py`/`excel_demo.py`'s setup steps updated to drop the now-gone `pip install -r requirements.txt`.

**Tools-only API surface, no reasoning required (not a numbered phase, its own PR):** the next step after the dependency split above — an explicit design decision that reasoning and tools usage stay separate: the integration layer should expose plain per-tool read/write APIs, with no assumption that *this* repo's `apm.agent.reasoner`/`ClaudeReasoner` is the only thing that can decide what to do with them. A future reasoning/voice layer, configured and deployed separately, is meant to call these directly instead of `/query` — never exposed to a customer/outside world directly, just the surface the APM app's own reasoning component (wherever it ends up living) is meant to use.

New router `src/apm/api/tools_routes.py` (mounted at `/tools/*` by `apm.api.app`'s `create_app`), one read + one write route per capability:
- `POST /tools/gmail/search`, `/tools/gmail/read` (reads, immediate) and `/tools/gmail/send` (gated)
- `POST /tools/calendar/search`, `/tools/calendar/read` and `/tools/calendar/create-event` (gated)
- `POST /tools/excel/worksheets`, `/tools/excel/read` and `/tools/excel/write` (gated)
- `POST /tools/actions/{process_id}/decision` — approve/reject any of the three gated writes above

Reads call the matching `apm.tools` method directly and return its data — no approval needed, same "read is always allowed" rule the existing flow already follows. Writes still cannot skip the non-negotiable human-approval gate just because the caller isn't this repo's own reasoner: `apm.agent.graph` gained `build_action_graph`/`start_action`, a second, smaller compiled graph (`propose -> approval -> execute`, no `fetch`/`reason`, no Anthropic dependency) that reuses the *exact same* `propose_node`/`approval_node`/`execute_node` logic `build_graph` uses for the reasoning flow — extracted into shared `_propose_node`/`_approval_node`/`_execute_node` factories so neither graph duplicates the gate. A `/tools/*` write route calls `start_action` with a caller-supplied `tool`/`method`/`payload` instead of `build_graph`'s `reason_node` producing one; the pending action, the interrupt, and the audit trail are identical either way.

Decisions for a `/tools/*` write go through `/tools/actions/{process_id}/decision`, deliberately not the existing `/processes/{id}/decision`: LangGraph's checkpointer replay needs the same compiled graph a process id was started against, so `apm.api.dependencies` gives `get_action_graph()` its own `MemorySaver`, separate from `get_graph()`'s — a process id crossing between the two would fail loudly (unknown thread id) rather than silently misbehaving. `get_tools()` is now its own cached dependency (both graphs, and the `/tools/*` read routes, share the one set of connectors); a write route checks the tool is configured *before* calling `start_action`, so an unconfigured tool (e.g. no `APM_EXCEL_WORKBOOK_PATH` set) returns a clean 503 immediately rather than creating a pending action doomed to fail once approved. `apm.api.app`'s own `_upstream_error`/`_to_response` helpers moved to a shared `apm.api._responses` module so both routers use the same error/response shape without importing from each other.

`tests/test_action_graph.py` (4 tests) covers the new graph directly (pause for approval, execute on approval, no execution on rejection, a second tool through the same graph instance); `tests/test_tools_api.py` (8 tests) covers the HTTP surface end to end (reads return data immediately with an audit-log entry, a write pauses and only executes after `/tools/actions/{id}/decision` approves it, rejection leaves nothing executed, an unconfigured tool 503s without creating a pending action). Full suite verified in two throwaway venvs exactly as the dependency-split entry above: `pip install -e .[integration-layer]` (141 passed, no nicegui, no Anthropic dependency touched by any of this) and `pip install -e .[ui,integration-layer]` (147 passed).

## Beyond phase 7b (not started — future phases, for discussion)

- Voice/avatar layer (LiveKit) — Layers 1–2 of the master architecture
- More tools (Jira, ERP/CRM, databases) per the workstream's capability-map pattern
- Cross-process search (one free-text query surfacing multiple matching orders, not just resolving to one)
- Production-grade persistence (swap the JSON store for Postgres) and real auth/RBAC for the dashboard itself
